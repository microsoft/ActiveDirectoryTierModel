## [2.1.0] - 2026-09-08

### Fixed
- **`config/tiermodel.schema.json` corrected to describe the real merged config shape (BUG-014)**: The schema was effectively fictional — `gpos` was declared as a flat array but is a 4-level nested object keyed by OU DN; `gpoStatus` listed 6 values including 2 invented names; `admx` was declared as an array but is an object; `groups`/`users`/`aclDelegations`/`winLapsDelegations` items used wrong property names throughout; and 7 top-level keys present in the merged runtime object were undeclared. The schema now describes what `Get-TierModelConfig` returns. Acceptance: `$merged | ConvertTo-Json -Depth 40 | Test-Json -Schema $schemaText` returns `True`; 10 of 18 segment files pass individually. `gpoStatus` enum is now limited to the 4 real `.NET GpoStatus` members. The `Get-TierModelConfig.ps1` help text was corrected: it no longer claims schema validation is performed.
- **`Test-TierModelConfig` phantom `scope` false-positive eliminated (BUG-017)**: `groups.items.required` in the schema declared a `scope` property that no product code reads or writes (real property is `groupscope`). All 29 shipped groups triggered "missing required property 'scope'" on every `Test-TierModelConfig` call. Fixed: `required` set to `["name","groupscope"]`; phantom `scope` removed from `properties`. Acceptance: `Valid=True ErrorCount=0` against real `tiermodel-groups.json`.
- **`Test-TierModelConfig` GPO mode validator, ADMX validator, and `denyApplyGroupPolicy` validator rewritten to match real config shape (BUG-018)**: All three validators were written against shapes the config has never had. (1) The GPO mode validator iterated the gpos container as a single PSCustomObject item → always emitted "GPO 'Unknown GPO' is missing required 'mode' property"; `ValidGpoModes` was always 0. (2) The ADMX validator looked for a `path` property; real config has a single object with `sourcePath` → always emitted "ADMX entry missing required 'path' property"; `ValidAdmxPaths` was always 0. (3) The `denyApplyGroupPolicy` validator checked for a phantom field named `denyApplyGroups` (which has never appeared in the config) instead of `denyApplyGroupPolicy`; also asserted group refs against config-defined groups — a false-positive trap, as the one real usage references built-in AD groups (`Domain Controllers`, `Read-only Domain Controllers`). All three rewritten in `TierModel.psm1`: `$flatGpos = @(if ...)` pipeline collection (prevents PowerShell single-element array unwrapping); `denyApplyGroupPolicy` shape-only validation (array of non-empty strings, no group-membership assertion); ADMX auto-detects `path` vs `sourcePath` with relative-path resolution against repo root. `$validGpoModes` extended with `'create'` (23 occurrences in shipped config). No production impact — `Test-TierModelConfig` is not called by Deploy or Audit, only exported for operator use. Five unit tests at `Unit.TierModelModule.Tests.ps1:328,344,614,624,633` that previously pinned the old phantom `denyApplyGroups` behavior have been rewritten to use the real `denyApplyGroupPolicy` field and assert shape-only validation (scalar → 1 warning; valid array → `ValidDenyApplyGroups` count); all five now pass, `It` count in that file is unchanged at 101, and the full Unit suite is 1573/0.
- **`Test-TierModelConfig -Scope` vocabulary mismatch silently skipped config validation and reported `Valid=True` (BUG-020)**: `Deploy-TierModel.ps1` lines 176–182 define 7 scope switches (`-OuOnly`, `-GroupOnly`, `-UserOnly`, `-GposOnly`, `-OuAclsOnly`, `-AdmxOnly`, `-FullDeployment`). The validator in `TierModel.psm1` branched on retired names (`GroupsOnly`, `UsersOnly`, `ImportAdmxOnly`) — only `OuAclsOnly` and `FullDeployment` matched. An unmatched scope fell through to the OU-only path and returned `Valid=True`; validation was skipped with no indication to the caller. Root cause: an incomplete refactor — `specs/001-tier-model-module/tasks.md` line 97 records T0043 retiring the legacy `ImportAdmxOnly` naming as COMPLETED, but the rename reached Deploy and Audit and never reached the validator. Additional defect: `-GposOnly` had no branch at all, so GPO schema validation and GPO-mode deep validation were gated to `FullDeployment` only. Fix applied in `TierModel.psm1`: all validator branches renamed to Deploy's vocabulary (`ImportAdmxOnly`→`AdmxOnly`, `GroupsOnly`→`GroupOnly`, `UsersOnly`→`UserOnly`); `GposOnly` added to both GPO validation gates; `[ValidateSet('OuOnly','GroupOnly','UserOnly','GposOnly','OuAclsOnly','AdmxOnly','FullDeployment')]` added to the `$Scope` parameter so a mismatch now fails at parameter binding instead of passing silently. 13 test call sites and the scope comment block updated. Verified: all 7 Deploy switches bind; all 3 retired names rejected at binding; Unit 1573/0, Integration 318/0.
- **Two diagnostic messages asserted an unproven cause and one advised an impossible remedy (BUG-021)**: `Resolve-TierModelPrincipalSid.ps1` and `Test-TierModelPrerequisites.ps1` both blamed the "Windows PowerShell compatibility shim" as a proven, known cause. Lab testing on Windows Server 2025 / PowerShell 7.5.1 shows AD and GroupPolicy commands report `CommandType = Cmdlet` (native, in-process), not `Function` (proxy shim) — the shim theory is not reproduced on our supported platform and the root cause remains unknown. (A customer on older RSAT could still encounter this scenario; the theory is not proven false.) Additionally, the remediation text advised "or run under Windows PowerShell 5.1", but `Deploy-TierModel.ps1:387` and `Audit-TierModel.ps1:210` both hard-block `PSVersion.Major -lt 7`, and `TierModel.psd1` declares `PowerShellVersion = '7.0'` — the remediation told the operator to do the one thing the scripts refuse to start on. Fix applied in both files: messages now describe the detected symptom (a deserialized `[String]` received where a live `[System.Security.Principal.SecurityIdentifier]` was expected, cause undetermined) rather than asserting a cause; the PowerShell 5.1 clause was deleted. Detection logic and fail-fast behaviour are unchanged. Verified: 3-line string-only diff, control flow untouched, `Unit.Prerequisites.Tests.ps1` 91/0.
- **`Test-TierModelConfig` had zero production callers — all schema hardening was unreachable in a real Deploy or Audit run (BUG-022)**: `Deploy-TierModel.ps1` and `Audit-TierModel.ps1` both loaded config via `Get-TierModelConfig` and immediately proceeded to plan/execute without ever calling the validator. All schema fixes from BUG-014, BUG-017, BUG-018, and BUG-020 were therefore dead code on the customer path. Fix: `$selectedScope` is now computed once, unconditionally, immediately after the scope-validation block in both scripts; `Test-TierModelConfig -Config $config -Scope $selectedScope` is called after the config-load `try/catch` on the primary (scope-based) path. **Deploy behaviour on failure:** `Write-TierModelFailFast` + `exit 1` — validation must block a broken config before any AD write. **Audit behaviour on failure:** prominent yellow warning block listing each error, then continues — Audit is read-only and refusing to run removes the operator's diagnostic tool when they need it most. **Include-only runs** (`-IncludeMsa` etc. with no scope switch) are explicitly excluded with a logged reason: the 7 scope validators cover OUs, Groups, Users, GPOs, ACLs, and ADMX but not the MSA, gMSA, dMSA, WinLaps, AuthSilos, or Audit config sections consumed by `-Include*`. **Deploy validation has three mutually exclusive branches — no path is silent:** (1) `$null -eq $selectedScope` → Include-only run, documented above; (2) scope active but `ConfigPath` absent from the config object → loud yellow warning that schema validation cannot run and deployment is proceeding with an UNVALIDATED config, also written to the log when `-Logging` is active (anomalous path, not a sanctioned test-fixture accommodation); (3) otherwise → validate, fail fast on errors, continue on warnings. **Audit false-success fix:** Audit previously printed a green "Configuration validation passed." when validation had thrown — `$configValidation` was `$null`, which fell through to the success branch. Audit now has three mutually exclusive states: threw (already warned, makes no success claim); returned errors (yellow block listing each error, continues); ran clean (green pass, with warnings listed if any). The secondary config loads at `Deploy-TierModel.ps1:2914` and `Audit-TierModel.ps1:1474` are both inside the standalone include-only entry path and are intentionally excluded. Warnings are printed in yellow and continue in both scripts. Verified: the earlier 7-scope clean result was re-verified after the BUG-023 fix — the original measurement was taken while the `-Config` validation path was inert and validating nothing; through the real schema path the shipped config is clean on all 7 scopes; a required OU `name` property removed is correctly rejected via `-Config` with `Valid=False`; Unit 1573/0, Integration 318/0; Joel's full lab validation pass on `TierLab-DC01` completed successfully.
- **`Test-TierModelConfig -Config` silently skipped all schema validation, leaving the BUG-022 wire-in weaker than documented (BUG-023)**: `Test-TierModelConfig` in `modules\TierModel\TierModel.psm1` (function begins line 140) supports two parameter sets: `FromPath` (`-Path`) and `FromConfig` (`-Config`). The entire schema-validation block was gated on `if ($PSCmdlet.ParameterSetName -eq 'FromPath' -and $schema)`, making it unreachable for `-Config`: the missing-required-property check, the `_validateArrayItems` helper, and all six of its call sites (`organizationUnits`, `groups`, `users`, `gpos`, `aclDelegations`, `admx`). Because `Deploy-TierModel.ps1` and `Audit-TierModel.ps1` both call `Test-TierModelConfig -Config $config -Scope $selectedScope` — the call added by the BUG-022 fix — the wire-in validated significantly less than documented; same silent-pass defect class as BUG-020. Proof: with a required OU `name` property removed, `-Path` returned `Valid=False` with 1 error while `-Config` returned `Valid=True` with 0 errors on the identical config; a broken OU parent path and an invalid `version` string were also missed under `-Config`. Fix: the `FromConfig` branch now resolves and loads the schema explicitly; the gate is reduced to `if ($schema)` so both parameter sets run full schema validation. Critically, a missing or unparseable schema now returns `Valid=$false` with an error instead of silently skipping validation — the failure mode is fail-closed, not fail-open. Customer impact: none shipped. The shipped config was re-verified through real schema validation (`-Path`) and is clean on all 7 scopes; this was a latent guard failure, not an active production break. Test fallout: one unit test in `tests\Unit.TierModelModule.Tests.ps1` had been written to exploit the bug (its own comment read "Uses FromConfig to bypass the FromPath schema block"); repaired with schema-complete fixtures; `It` count unchanged at 101; no assertions weakened. Verified: Unit 1573/0, Integration 318/0; Joel's full lab validation pass on `TierLab-DC01` completed successfully.
- **`config/tiermodel.schema.json` — `gpoStatus` enum reduced from 6 to 4 real values (BUG-016, partial)**: `AllEnabled` and `BothSettingsDisabled` were invented names not present in `Microsoft.GroupPolicy.GpoStatus`; removed from the schema enum. The 4 real values with their AD `flags` mappings are: `AllSettingsEnabled`→0, `UserSettingsDisabled`→1, `ComputerSettingsDisabled`→2, `AllSettingsDisabled`→3. ⚠️ The AD `flags` values are **not** the .NET enum ordinals — `AllSettingsEnabled` is ordinal 3 but flags 0; do not "correct" the mapping.
- **Deploy-side `gpoStatus` now fails loudly on unrecognised values (BUG-016)**: `New-TierModelGpo.ps1:L167-175` now validates `gpoStatus` against the 4-value list and throws on an unrecognised value; the throw is caught by the per-GPO error handler (L282), failing that GPO and continuing the run. The `switch` at L200-204 has exactly 4 cases and no `default`. Previously a typo'd `gpoStatus` silently deployed with flags 0 (all settings enabled). Fixed in code on 2026-09-04; validated in the lab by Joel Platek on 2026-09-04.
- **Shared test stubs in `tests/helpers/ADStubs.ps1` now return objects matching real cmdlet contracts (BUG-015)**: All AD and GroupPolicy cmdlet stubs previously had empty bodies returning `$null`; production write-verification checks would then throw on a successful call. `Set-GPRegistryValue` (L151, L175) and other GroupPolicy cmdlets now return PSCustomObject unconditionally, matching their real return contract (no `-PassThru`). AD cmdlets including `Set-ADObject` (L51, L102), `New-ADGroup`, `New-ADOU`, auth-policy and auth-silo cmdlets now return PSCustomObject only when `-PassThru` is specified, matching the real AD module contract. These stubs execute only under Pester, not during a lab run; the fix is proven by the green test suite (Unit 1573/0, Integration 318/0). Joel Platek's 2026-09-04 full lab pass over all Deploy and Audit scenarios found no related regressions.
- **Domain Admin membership check rewritten for compatibility-shim immunity (BUG-013)**: The prerequisite now uses a token-groups check (`[WindowsIdentity]::GetCurrent()` + `AccountDomainSid` + RID 512) that runs **first** and independently of the ActiveDirectory module — immune to deserialization. This check handles null/workgroup `AccountDomainSid` explicitly and fails closed. The AD module import block is demoted to environment classification for remediation wording and compat-shim detection (fail-fast guard). The exception catch-all no longer relabels every failure as "Domain Admin membership required" — it now reports the real error message: `Unable to verify Domain Admin membership: <actual message>`. Lab-validated: 1,573 unit tests passing, PSScriptAnalyzer clean, silent-deploy-failure cases (compat shim + SID resolution) confirmed fixed.
- **`Resolve-TierModelPrincipalSid` hardened against deserialized SID loss (BUG-013, escalation)**: New private (non-exported) `ConvertTo-TierModelSidString` helper accepts a live `SecurityIdentifier`, a deserialized `String`, a `byte[]`, or a PSObject with `.Value`; it validates and round-trips through the `SecurityIdentifier` constructor and **throws on empty/malformed** rather than returning a blank SID. Applied at all five call sites (L96, L346, L360, L375). Blank SIDs now surface as `Source='ADError'`, `Success=$false` with the real reason instead of silently degrading to `NotFound`. This is load-bearing: the resolver feeds GPO `GptTmpl.inf` (User Rights Assignment and Restricted Groups), where a blank principal is a silent security-config failure. `Compare-TierModelAuthSddl.ps1:110` was assessed and deliberately NOT changed — it is a read-only fallback that already fails safe.
- **False "Missing GPOs: 0" in the GPO audit summary**: `Test-TierModelGPOAudit.ps1` printed a hardcoded literal `0` on the *Missing GPOs* summary line, so an audit could report all-green while GPOs were genuinely absent from the directory. The summary now prints the real `$missingGpoCount` (`Test-TierModelGPOAudit.ps1:438`, displayed at L459–L462) and the whole summary was rebuilt on **mutually exclusive** failure buckets — `Missing` → `Error` → `Mismatch` (L438–L453) — so nothing is double counted and no figure is a hardcoded literal or derived by subtraction. `TotalIssues` is now `missing + error + mismatch` (L453) and drives Overall Status; the former `$driftCount = $totalFailed + $errors.Count` double-count is gone. This was the highest-leverage fix on this branch.
- **GPO enabled-state check was a guaranteed false positive**: a newly added enabled/disabled assertion in `Test-TierModelGPO.ps1` was reverted to an **`Info`-only** check (`Test-TierModelGPO.ps1:231–275`). It records `GpoStatus` / `SettingsDisabled` and a `DeliveryNotes` entry, never writes to `Issues`, and never influences the Pass/Fail verdict. Design rule now stated in code: some GPOs ship deliberately with settings or links disabled (for example a customer running the SHF baseline instead of the Microsoft SCT baseline), and neither state may fail an audit. The audit summary reports these separately as *"Present but Delivering No Settings (informational, not a finding)"*, deliberately outside the failure buckets (`Test-TierModelGPOAudit.ps1:450`).
- **Audit now fails loudly on an unrecognised `gpoStatus`**: `Test-TierModelGPO.ps1:166–198` replaced a `switch` whose silent `default` meant "expect `AllSettingsEnabled`" — so a typo in configuration could be reported as **Pass** — with a validated `[ordered]` lookup table. An unrecognised value now produces a per-GPO `Fail` naming the offending value and listing the valid set. This is deliberately a per-GPO failure and **not** a `throw`, so one bad configuration value cannot abort an entire audit run.
- **Permanent unresolvable `gpoStatus` drift between deploy and audit**: The original `New-TierModelGpo.ps1` `switch` for `gpoStatus` handled only 4 cases and `AllSettingsDisabled` fell through `default { 0 }`, deploying as flags 0 (all settings enabled). `Test-TierModelGPO.ps1` expected flags 3 for `AllSettingsDisabled`. Because re-running deploy kept writing 0, the drift could never converge. Both `New-TierModelGpo.ps1` and `Test-TierModelGPO.ps1` now map the same **4 real `Microsoft.GroupPolicy.GpoStatus` values**: `AllSettingsEnabled`→0, `UserSettingsDisabled`→1, `ComputerSettingsDisabled`→2, `AllSettingsDisabled`→3. Each file carries a comment requiring the two tables to stay in agreement. Deploy now validates the value against the 4-value list before the switch and throws on any unrecognised string; the throw is caught per-GPO, failing that GPO and continuing the run. Latent in practice: the shipped `config/tiermodel-gpos.json` uses only `UserSettingsDisabled` and `ComputerSettingsDisabled`, so no live deployed GPO was misconfigured by the old code.
- **`enforced` GPO-link defect silently enforced existing links on re-run**: `New-TierModelGPOLink.ps1:79` and the two planner twins `Get-TierModelGPOLink.ps1:59` and `Get-TierModelGpoLinkFd.ps1:62` defaulted a missing `enforced` configuration key to the **string** `'No'`. In PowerShell every non-empty string is truthy, so `if ('No')` is `$true` and the update path then called `Set-GPLink -Enforced 'Yes'` against an **existing, possibly production, link** — violating the project rule *never modify an already-linked GPO*. The default always applied: `config/tiermodel-gpos.json` contains **zero** `enforced` keys across all **146** GPOs. It only fired on **re-runs** — a fresh deployment takes the creation path, which was correct — which is why earlier release testing never caught it. All three sites now default to `$null` ("not specified, never assert") and evaluate with `($x -eq 'Yes' -or $x -eq $true)`; the update guards are `if ($null -ne $requiredEnforced -and $requiredEnforced -ne $currentEnforced)` (`New-TierModelGPOLink.ps1:145`, `:164`; `Get-TierModelGPOLink.ps1:141`). Note for future maintainers: casting to `[bool]` is the **wrong** fix here, because `[bool]'No'` evaluates to `$true`.
- **Converged GPO-link plan reported `GPOLinkPlanningFailed`**: in `Get-TierModelGPOLink.ps1:207–215` the sort pipeline collapsed to `$null` when it yielded 0 or 1 items, and `$null.Count` throws under `Set-StrictMode -Version Latest` — so a **fully converged (successful)** plan was reported as a planning failure. Fixed with an `@()` array guard around the pipeline.
- **Unverifiable AD/GPO writes reported success when nothing was written**: a shared root cause, fixed once and applied across the write paths. The tool requires PowerShell 7, so the ActiveDirectory and GroupPolicy modules load through the Windows PowerShell compatibility shim as **script proxy functions** that report failure via `$PSCmdlet.WriteError()` — which ignores an *inherited* `$ErrorActionPreference = 'Stop'`. Only an **explicit** `-ErrorAction Stop` plus a non-null result check makes such a write verifiable. This is the mechanism behind the original "deployment reports success but nothing happened" symptom. Explicit `-ErrorAction Stop` and result checks (via the new `Get-TierModelWriteFailureDetail` diagnostic helper) were added to `New-TierModelWinLapsAcl.ps1:185`, `Set-TierModelAuthSiloMembership.ps1:201` and `:218`, `New-TierModelGpo.ps1:181`, `New-TierModelGPOLink.ps1:125`/`:166`, `New-TierModelGroup.ps1`, `New-TierModelOu.ps1`, `New-TierModelAuthPolicy.ps1`, `New-TierModelAuthSilo.ps1`, `New-TierModelUser.ps1` (`New-ADUser` and `Add-ADGroupMember`) and `Import-TierModelGpo.ps1` (`Import-GPO`). A failed group-membership add on a user is now recorded as a `UserGroupMembershipFailed` error and clears `Converged`, instead of being silently counted as executed.
- **GPOs dropped from the plan by an unmet dependency were never named**: `Get-TierModelGpo.ps1` now records every GPO removed from the plan together with its specific blocking reason (missing target OU, or missing required group) and returns `SkippedGpos` plus a `SkippedGpoSummary` grouped by reason (`Get-TierModelGpo.ps1:65–67`, `:729–731`). `Deploy-TierModel.ps1` renders them through the new `Write-TierModelSkippedGpoReport` / `Write-TierModelBlockedOutcome` helpers so the operator is told exactly which GPOs were not deployed and why, rather than only seeing deduplicated dependency errors.
- **`ExistingCount` / `TotalInConfig` reported meaningless values**: both `Get-TierModelGpo.ps1` (`:704`, `:729–731`) and `Get-TierModelOuAcl.ps1` derived "already exists" by subtracting total actions from total configuration entries. For `Get-TierModelOuAcl` that planner only ever emits `CreateAcl` actions, so the subtraction was structurally always zero. Both now count real objects found in AD (`$existingGpoNames`, `$existingAclCount`) and report `TotalInConfig` from the configuration directly.
- **One ADMX/ADML source-hash mismatch aborted the entire ADMX phase (BUG-012)**: `Copy-TierModelAdmx.ps1` treated every analysis error as fatal, so a single missing file or MD5 source-hash mismatch — most commonly a CRLF/LF line-ending difference from downloading GitHub's *Source code (zip)* rather than the release asset — stopped the phase and **nothing** was deployed. `Copy-TierModelAdmx.ps1:74–99` now classifies analysis errors into **per-file (recoverable)** and **fatal (abort)** using the pattern `'^Source (ADMX|ADML) file (not found|hash mismatch)'`. Per-file errors skip only the affected file, are surfaced as warnings and recorded in `AdmxSkipped` / `AdmlSkipped`, and all remaining files still deploy; only genuinely fatal errors (unreadable configuration, unreachable DC or central store, or an exception from `Get-TierModelAdmx`) still `throw "Cannot proceed with deployment due to analysis errors"`, because a half-built plan must never be deployed silently. The upstream skips are at `Get-TierModelAdmx.ps1:119–122` (ADMX) and `:180–183` (ADML), which record the mismatch and `continue` to the next file.
- **Module file logging was dead code**: the module declared `$script:LoggingEnabled` / `$script:DefaultLogPath` but nothing ever set them, so every in-module `Write-TierModelLog` call went to the console streams only and never reached disk. `Initialize-TierModelLogging` is now defined inline in `modules/TierModel/TierModel.psm1:14` and entry scripts invoke it inside module scope (`TierModel.psm1:45`), producing real log files. It is deliberately **not** placed in `modules/TierModel/public/` — `tests/Unit.ModuleManifest.Tests.ps1` builds its expected export list from the *filenames* in that folder, so any new file there breaks the manifest test regardless of whether the function is exported. Logging remains opt-in.
- **A standalone audit could print a green COMPLIANT headline with an error count listed directly beneath it**: errors now outrank drift in the standalone verdict. A run that could not complete every check reports `COMPLIANCE COULD NOT BE FULLY DETERMINED` with the error count, in red, instead of claiming compliance. The consolidated report already applied this rule; the standalone renderer now matches it.
- **A scope with nothing configured reported as compliant, and two compliance figures were a hardcoded 100%**: a scope with no configured objects now reports `Not checked - nothing configured` in neutral grey, and is excluded from the compliance calculation entirely — it contributes to neither the numerator nor the denominator, and can never render green. A scope that **is** configured but resolves to zero live objects still reports drift, exactly as before; the two situations are deliberately distinct and are now told apart.
- **A directory that could not be read reported as compliant**: the group and user checks captured the read failure and then discarded it, so an unreachable or unreadable directory rendered as clean. Both now report the affected objects as **unverified** rather than passed — an object we could not read is not a pass — matching the behaviour the OU check already had.
- **Missing counts in the audit summaries were hardcoded zeros**: every *Missing* figure is now derived from the measured values, so an audit can no longer report zero missing objects while objects are genuinely absent from the directory.
- **Drift findings were coloured by exact string match, so genuine failures rendered as yellow advisories**: colouring is now driven by the severity class of the finding rather than by matching its label against a list of literals. Missing ACLs, missing audit rules and errors now render **red**; a finding no longer gets downgraded to yellow merely because its label was not in the renderer's list.
- **A failed audit-rule check was labelled with a name that did not say it had failed**: an audit-rule finding in the FAILED state is now labelled **MissingAuditRule**, which names the actual condition, instead of the state-agnostic `AuditRight`, which read identically whether the rule was present or absent.

### Added
- **`gpoStatus` enum in `config/tiermodel.schema.json`** corrected to the **4 real `Microsoft.GroupPolicy.GpoStatus` members** (`AllSettingsEnabled`, `UserSettingsDisabled`, `ComputerSettingsDisabled`, `AllSettingsDisabled`). The enum provides editor / IntelliSense guidance and is also read at runtime by `Test-TierModelConfig` (an exported function defined inline in `TierModel.psm1`, running under `Set-StrictMode -Version Latest`). Schema keys read by `Test-TierModelConfig` are therefore **load-bearing**: removing them throws `PropertyNotFoundException` at runtime. Safe access pattern: `$definition.PSObject.Properties['key']` rather than `$definition.key`. `Test-Json` appears nowhere in product code; `gpoStatus` enforcement at deploy and audit time lives in the lookup tables in `New-TierModelGpo.ps1` and `Test-TierModelGPO.ps1`, not in the schema.
- **`-EnableVerbose` and `-EnableDebug` diagnostic switches on `Deploy-TierModel.ps1` and `Audit-TierModel.ps1`**: opt-in, run-scoped diagnostics for exactly the situation that prompted them — a customer deployment in which two GPOs silently failed to be created, with no error message on screen and no way to determine why after the fact. `-EnableVerbose` surfaces what the run is doing and against which target; `-EnableDebug` adds the internal decision detail. Either switch enables logging for that run and announces on screen that it has done so. **Both switches change only what is recorded — never what is decided, and never what is written to Active Directory.**
- **The switches are named in full — `-EnableVerbose` and `-EnableDebug` — deliberately, rather than reusing PowerShell's `-Verbose` and `-Debug`**: the built-in common parameters therefore stay available and unshadowed, and continue to mean what they normally mean. An operator can use either set, or both, without one silently overriding the other.
- **Implemented through preference variables, not per-cmdlet forwarding**: the switches set `$script:VerbosePreference` / `$script:DebugPreference` for the duration of the run instead of forwarding `-Debug` to individual cmdlets. One switch therefore reaches every call site in the run, including code added later, and nothing has to be remembered at each call. The preferences are restored when the run ends, including on an early exit.
- **An unredacted transcript is written when both switches are supplied together**: with `-EnableVerbose` **and** `-EnableDebug`, a full session transcript is written to a `Debug\` subfolder, kept separate from the normal log file, which is unchanged. ⚠️ **The transcript is unredacted by design** and can contain distinguished names, account names, SIDs and other environment detail. Treat it as sensitive: review it before attaching it to a support case or sharing it outside your organisation. The warning is printed on screen and is also written inside the transcript itself, so it travels with the file.
- **The log base filename and output format prompts now have working defaults**: pressing Enter at either prompt accepts the shown default instead of failing with an error. Duplicated resolution text was removed from the Windows LAPS schema errors, every previously-bare dMSA prerequisite error gained a remediation step, and `Audit-TierModel.ps1` gained a matching PowerShell-version gate.
- **OU "Block GPO Inheritance" is now verified and retried during deployment (BUG-010)**: creating an OU with `blockGpoInheritance` (or `disableInheritance`) previously called `Set-GPInheritance -IsBlocked Yes` (or `Set-Acl` protection) once and reported success as long as the call did not throw — but the change intermittently did not persist (a silent no-op, ~10% per OU on a fast run), leaving a tier boundary unblocked while the deployment still reported success. `New-TierModelOu` now reads back `Get-GPInheritance` (and the ACL's `AreAccessRulesProtected`) on the same DC and retries up to 4 times with backoff until the setting is verified; if it still cannot be confirmed it records a human-readable error ("Block GPO Inheritance flag was not set for OU 'X'…") instead of a false success. In `-FullDeployment`, an unverified OU inheritance setting hard-stops the run before the Groups phase so a tier boundary is never silently left open. The logic remains create-only — existing/live OUs are never modified (remediate drift via change control and confirm with the audit script).
- **Windows LAPS audit no longer false-flags tier admins that hold OU full control (BUG-009)**: `Test-TierModelWinLapsAcl`'s `UnexpectedAcl` detection (added in BUG-004) uses `Find-LapsADExtendedRights`, which resolves a principal's *effective* LAPS read — including access granted implicitly by `GenericAll` (full control). Because the Tier Model's own OU-management delegation grants tier admin groups (e.g. `Tier0Admins`/`Tier1Admins`) `GenericAll` on their Member-Server OUs, every audit flagged them as unexpected LAPS readers even though they hold no *explicit* ms-LAPS delegation. The audit now collects the OU's `GenericAll` (Allow) holders from the same DACL it already reads for SELF detection and excludes them from the unexpected-holder check, so a genuinely unexpected *explicit* LAPS reader is still flagged while `GenericAll`-derived effective access is not. Full-control drift remains covered separately by the OU ACL audit. (Lab-validated: the two recurring `Tier0Admins`/`Tier1Admins` warnings are gone and an injected explicit LAPS holder is still detected.)
- **Clean deployment no longer reports phantom "Skipped" items (BUG-011)**: a brand-new `-FullDeployment … -ConfirmApply` reported `Skipped: 4` despite creating everything with zero real skips. The User and OuAcl result objects built their `Applied`/`Skipped` arrays with `@(1..$executionResult.Skipped | ForEach-Object {…})`; when the count is `0`, PowerShell's `1..0` is a **descending** range (`{1, 0}`, two elements), so each of those two phases emitted 2 phantom "Skipped" entries → `Skipped: 4`. All four `1..$n` ranges (the User and OuAcl `Applied` and `Skipped` builders) are now guarded with `if ($n -gt 0)` so a zero count yields an empty array; real applied/skipped counts are unchanged.
